Download Is a Different Problem — Mostly Already Solved

Lessons 1 and 2 covered the upload side: your Upload Session, chunk index, bitset, checksum split — all hand-rolled, on purpose (ADR 0001). Download needs the same properties — resumable, bounded memory, parallelizable — but your project built it almost entirely differently. That difference is the lesson.

Why hand-roll upload but not download

Uploading a file is fundamentally something HTTP has no native primitive for — there's no standard "resume a POST from where it dropped" mechanism, which is exactly why tus.io and S3 multipart exist as bespoke protocols on top of HTTP, and why your project built its own Upload Session concept to match.

Downloading part of a resource, on the other hand, has been a solved standard since HTTP/1.1. HTTP Range requests let a client ask for a byte range of a resource instead of the whole thing, and every HTTP client (browsers, curl, everything) already speaks it. Your project's own research (docs/research/modern-huge-file-transfer.md §6) is explicit about this: reuse the standard primitive on the download side, rather than hand-rolling a parallel "download manifest" concept that HTTP already gives you for free.

The transferable lesson here isn't "how Range requests work." It's the judgment call itself: ADR 0001 hand-rolls the upload protocol for learning value — and issue #5's design explicitly does not extend that same reasoning to download. Knowing when NOT to reinvent something is as much a design skill as knowing how to build it. A solved standard sitting right there is a reason to stop, not a challenge to out-engineer.

The mechanism: Range, Accept-Ranges, 206, If-Range

Four pieces, straight from the standard (MDN: Range header):

  • Range: bytes=0-8388607 — the client asks for a specific byte span (here, the first 8MiB).
  • Accept-Ranges: bytes — the server advertises that it supports this.
  • 206 Partial Content — the success response, carrying only the requested bytes plus a Content-Range header saying which slice of the total this is.
  • If-Range — a conditional check tied to a validator (an ETag or a Last-Modified date). If the validator still matches, the server sends the requested 206 partial; if the underlying resource changed since the client last saw it, the server sends the full 200 OK instead — refusing to splice bytes from two different versions of the file together.

If-Range is the piece worth sitting with. It's solving the exact same problem upload resume solves with the offset/409 pattern from Lesson 1 — "how do I know what I'm resuming still matches what I already have" — just expressed as a standard header instead of your own Upload Session state. Same problem, two different mechanisms, because one side of the transfer had a standard answer and the other didn't.

What your project actually built

From issue #5's resolution:

Server

  • Same Upload Id end-to-end — no separate download identity is minted. GET /uploads/{id}/download serves the bytes once the session is COMPLETE.
  • Range parsing is not hand-parsed — Spring's built-in ResourceRegion/HttpRange support does it (Spring reference docs). Reuse, per the reasoning above.
  • If-Range is keyed on an ETag built from the same whole-file SHA-256 checksum computed at Assembly in Lesson 2 — content identity, not a filesystem timestamp. One checksum, two jobs.
  • No per-range checksums on the way out. The assembled file is already a verified, static artifact (Lesson 2's SHA-256 pass proved that once); re-checksumming ranges on every read would burn CPU the single vCPU doesn't have to spare, for a guarantee TLS already provides in transit.

Client

  • Parallel fetch() calls against ranges aligned to the same 8MiB unit used for upload chunks — one chunk-size concept for the whole app, not two.
  • Disk writes are the interesting constraint: fetches run in parallel, but they all funnel through one FileSystemWritableFileStream, serialized via positional writes. The File System Access API doesn't support true concurrent writers on one file handle — so parallelism here buys you overlapping network latency, not overlapping disk writes. (Which the 1-vCPU box wasn't going to give you concurrent write throughput for anyway.)
  • This is Chromium/Edge only — showSaveFilePicker/createWritable() aren't available in Firefox at all, and Safari's support is too recent to rely on. A cross-browser fallback was explicitly ruled out of scope, and the UI feature-detects and shows a disabled state instead of failing silently.
  • A received-ranges bitset in IndexedDB mirrors the server's chunk bitset from Lesson 1 — same resume pattern, client side this time. The FileSystemFileHandle itself is also persisted (it's structured-cloneable) and re-permissioned on resume, so the client never has to ask the user to re-pick the file.
  • Resume is user-initiated, not automatic — matching the upload side's model from Lesson 1.
  • After all ranges land, the client recomputes SHA-256 over the whole downloaded file and compares it to the server's checksum. "Every byte range arrived" only proves coverage — it doesn't prove correctness. That's the same distinction ADR 0002 draws between per-chunk and whole-file checks, just run once more, client-side.

Which standard HTTP header does the server use to make sure a resumed download can't silently splice bytes from two different versions of the file?

Parallel range fetches overlap network latency, but which single resource still has to be accessed serially through one writable stream, because the File System Access API doesn't allow concurrent writers on one file handle?

The pattern, generalized

Before reaching for a bespoke protocol, ask: does a standard already solve this half of the problem? Upload needed one because HTTP has no native resumable-POST concept. Download didn't, because Range requests already are that concept — and had been for decades before this project existed. The skill worth carrying forward isn't "always hand-roll for learning" or "always reuse the standard" — it's making that call deliberately, per problem, instead of applying one instinct uniformly across a whole system.
