One State Machine, Two Directions

Lessons 1–3 built the protocol: chunk + resume on upload, a checksum split matched to threat model, and Range requests reusing an existing standard on download. Two different mechanisms, two different endpoints — but by the time the frontend needed to drive both, your project noticed something: upload and download are the same state machine wearing different clothes. That recognition is what useTransfer is built on.

Spot the shared shape first

Look at what upload and download both actually need, independent of direction:

  • A record of which pieces have been transferred so far — a bitset (Lesson 1's chunk bitset; Lesson 3's range bitset — same idea, same 8MiB unit, different endpoint).
  • Byte-level progress, computed off that bitset, not a raw chunk count.
  • Pause (stop sending new requests, keep state) and cancel (stop and discard state).
  • Retry with backoff when a single unit fails.
  • A concurrency ceiling — 3–4 units in flight at once, from the same CPU-budget reasoning that shaped Lessons 2 and 3.

None of that list mentions "chunk" or "range" specifically. It's direction-agnostic. What does differ between upload and download is narrow: how you get one unit of data, how you send/fetch it, and how you persist progress across browser sessions.

This is the same design move as Lesson 2's checksum split — separate what's genuinely different (fast-vs-strong hash) from what can be unified (one Checksum concept, two algorithms). Here it's: separate what's genuinely direction-specific (get/send a unit) from what's shared (track progress, pause, retry, throttle concurrency). Once you can name which parts of two similar-looking problems are actually the same, the shared part becomes one implementation instead of two.

What your project actually built

From issue #6's design, implemented in frontend/src/hooks/useTransfer.ts:

  • One core hook, useTransfer, owns the shared state machine — bitset, byte-progress math, pause/cancel, retry-with-backoff, the concurrency queue. It's parameterized by a small interface: "how do I send/fetch one unit" and "how do I persist state" are supplied by the caller, not baked in.
  • Two thin wrappers, useUploadTransfer and useDownloadTransfer, supply only the direction-specific pieces: Manifest creation vs. status-check, chunk PUT vs. range GET, a lazy File.slice() read vs. a File System Access write.
  • Concurrency (3–4 units in flight) is owned by the core hook as a small worker-pool queue — it pulls pending chunk/range indices, fires a request per open slot, and refills as each settles. This isn't something the networking library gives you for free; the hook supplies it.
  • Retry rides on TanStack Query's built-in mutation backoff — a checksum mismatch (Lesson 2's per-chunk CRC32C check failing server-side) is treated exactly like a network error: same index, re-sent.
  • Progress is computed in bytes, read off the bitset — (completed units × 8MiB) + exact size of a completed final unit, divided by total size — not a raw count of completed chunks. A byte-accurate progress bar and a chunk-count one look identical until the last, undersized chunk throws the count-based version off.

Where hashing lives

One detail that's easy to miss: CRC32C and SHA-256 (Lesson 2) run in a Web Worker that only hashes — it takes an ArrayBuffer, returns a checksum via postMessage, and does nothing else. Networking stays on the main thread through TanStack Query, so its devtools, caching, and retry all keep working normally. This is a narrow, deliberate split: move the CPU-heavy part off the render thread, but don't drag networking along with it just because both happen to touch the same chunk of bytes.

Pause and cancel aren't symmetric

Both stop in-flight requests via an AbortController — no request keeps running unsupervised. But they diverge on what happens to state:

  • Pause keeps everything: the server-side Upload Session stays UPLOADING (Lesson 1's state machine — already-received chunks are kept), and the local IndexedDB bitset stays intact. Resume just continues pulling from the same queue.
  • Cancel does the same abort, then deletes the local IndexedDB record. Notice there's no cancel endpoint on the server — an abandoned session is simply left to expire via the 24h TTL sweep from Lesson 1's reference sheet (issue #4). The client doesn't need to tell the server "I quit"; the server's own cleanup already handles that case.

That's a small but real design choice: rather than building a cancellation protocol, the project noticed an existing mechanism (the TTL sweep, already needed for crashed browsers and dead connections) already covers the "user cancelled" case too. One less endpoint, one less thing that can get out of sync.

The pattern, generalized

Whenever two features look similar but not identical — upload/download here, but just as easily "create" and "edit" forms, or "import" and "export" pipelines — the move is: list what's actually shared (state, progress, retry, throttling) separately from what's genuinely different (the one send/fetch primitive), then build exactly one implementation of the shared part with a narrow seam for the differences. Unifying too early (forcing download to literally reuse an upload-shaped function) or too late (two parallel, drifting copies of the same state machine) both cost you later — the seam has to sit exactly where the real difference is, no wider.
