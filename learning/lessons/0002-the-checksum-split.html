One Hash Isn't Enough: The Checksum Split

Lesson 1 established the shape: chunks, an Upload Session, a bitset tracking what's arrived. But chunks can still arrive corrupted — a truncated request, a flaky disk sector, a flipped bit on the wire. Something needs to verify integrity. The obvious move is "hash everything with SHA-256, it's the strong, trusted choice." Your project deliberately didn't do that everywhere. Understanding why is the point of this lesson.

The naive answer breaks the CPU budget

Your server has 1 shared vCPU — the same core running Spring Boot's request handling, disk I/O, and whatever hashing you ask it to do. SHA-256 is a cryptographic hash: it's deliberately expensive to compute, because that expense is what makes it collision-resistant against an adversary trying to forge a hash. Hashing every 8MiB chunk of a 5GB upload with SHA-256 means paying that cost roughly 640 times per file, competing with everything else for the one core you have.

CRC32C is a different kind of hash entirely — non-cryptographic, and on modern x86 CPUs (basically anything since Intel Nehalem) it runs on a dedicated hardware instruction (SSE4.2 crc32). That hardware acceleration puts its theoretical throughput around 20.5 GB/s per core — roughly an order of magnitude past what a general-purpose cryptographic hash manages on the same core.

The trap to avoid: "SHA-256 is stronger, so use it everywhere" sounds like the safe default. But strength that costs CPU you don't have isn't safety — it's a bottleneck disguised as caution. The right question isn't "which hash is strongest," it's "what am I actually defending against, and what can I afford to pay for it?"

Match the hash to the threat model

This is the move your project's ADR 0002 makes explicit. Ask: who or what is this checksum defending against?

  • Accidental corruption — truncated request, flaky disk, a bit flipped in transit. This is the actual threat for a single trusted user uploading their own files. CRC32C catches this cheaply and immediately.
  • Deliberate forgery — an attacker crafting bytes that hash to the same value to slip corrupted or malicious data past your checksum unnoticed. This is what SHA-256's collision-resistance defends against — and it's not your threat model here. There's no untrusted uploader in a single-user lab.

So the split isn't "fast hash vs. strong hash, pick one." It's two different hashes for two different jobs, applied at two different points:

  • CRC32C, per chunk, checked on arrival. Cheap enough to run ~640 times per 5GB file without denting the CPU budget. Catches the accidental-corruption threat immediately — you find out a chunk is bad the moment it lands, not after the whole file is assembled.
  • SHA-256, once, over the whole assembled file, at Assembly. Expensive, but paid exactly once per upload instead of once per chunk — the cost that would be prohibitive 640 times over is fine as a single pass. This gives you a strong end-to-end guarantee at the point it's cheapest to afford.
Not a hypothetical trend, either. Even Amazon S3 — built for a much larger threat surface than this lab — now defaults new multipart uploads to CRC64NVME instead of a SHA-family hash, explicitly favoring a fast CRC variant for routine integrity checking. The industry has been converging on exactly this split, not away from it.

CRC32C protects against accidental corruption. What threat does it deliberately NOT protect against — the one SHA-256 exists for?

At which single point in the Upload Session's lifecycle does the one SHA-256 pass over the whole file happen?

The pattern, generalized

Strip away the specific algorithms and this is a reusable move for any resource-constrained system doing integrity checking at scale:

  1. Identify what you're actually defending against — accidental failure, or a deliberate adversary. They're different problems with different-cost solutions.
  2. Apply the cheap defense at high frequency (per-unit, catches problems early, minimal resource cost).
  3. Reserve the expensive defense for the lowest frequency you can get away with (once per whole operation, not once per piece).

This is the same shape as, say, a build pipeline running fast linters on every save but a full expensive test suite only on merge — or a database checksumming pages cheaply on every read but running an expensive deep-consistency check only nightly. Once you see "cheap-often + expensive-rarely, matched to the actual threat" as a pattern, you'll recognize when a project is over-paying for uniform strength it doesn't need.
