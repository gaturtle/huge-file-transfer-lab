Why Chunk, Why Resume

Imagine you're uploading a 5GB video file from a browser to a server, over home Wi-Fi, to a box with 1GB of RAM. Two things go wrong with the naive approach — <input type="file"> → one big POST of the whole file:

  1. Memory. If the server reads the whole request body into memory before processing it, a 5GB upload alone blows past a 1GB box. It doesn't matter how good your code is — the file doesn't fit.
  2. Fragility. Home Wi-Fi drops. If the connection dies at byte 4.9GB of 5GB, a single-request upload has to restart from byte zero. On a slow link, that's the difference between "annoying" and "never actually finishes."

This is exactly the problem your project's CONTEXT.md domain model exists to solve, and it's the same problem tools like tus and S3's multipart upload solve — just with different wire formats. The pattern is the same everywhere; only the details differ.

The core idea: split, track, resume

Instead of one giant request, the client slices the file into fixed-size pieces — in this project, 8MiB Chunks — and uploads them one at a time (or a few in parallel). The server doesn't just receive bytes; it keeps a record of which chunks it has. That record is the Upload Session.

This one move — tracking progress at the chunk level instead of the whole-file level — is what buys you both properties at once:

  • Bounded memory: the server only ever holds one 8MiB chunk in flight, never the whole file.
  • Resumability: if the connection dies mid-upload, the client asks "which chunks do you already have?" and sends only the rest. Nothing already-received is wasted.
This is not a hypothetical. Your project's load test (issue #18) proved it: a 5GB upload through this exact mechanism peaked at ~338MB of memory — comfortably inside a 1GB box — with no OOM kill.

The state machine you actually built

Your Upload Session isn't just "has some chunks" — it moves through explicit states, decided in issue #3:

UPLOADING → ASSEMBLING → COMPLETE or FAILED

UPLOADING is where chunks arrive, tracked by a per-session bitset (issue #4 — SQLite-backed). Once every chunk index has arrived, the client tells the server to finish, and the session moves to ASSEMBLING — a single checksum pass over the reassembled file. That resolves to COMPLETE (checksum matched) or FAILED (it didn't) — both terminal. A FAILED session is never resumed; the client opens a fresh one.

Notice what's not in this state machine: there's no "paused" state on the server. Pause/resume is entirely a client-side decision about when to keep sending chunks — the server doesn't need to know the difference between "briefly paused" and "connection just dropped." That simplification is only possible because progress is tracked per-chunk, durably, on the server.
