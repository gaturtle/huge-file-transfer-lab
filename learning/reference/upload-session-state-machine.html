Upload Session State Machine

The compressed shape of the resumable-upload pattern used in the Huge File Transfer Lab. Source of truth: issue #3 — Design the chunk & Upload Session protocol and issue #4 — persistence & staging.

Key design facts

  • Chunks are addressed by index, not byte offset. Offset is derived (index × 8MiB), never transmitted.
  • Resume = client asks GET /uploads/{id} for which chunks the server already has (a bitset), then sends only what's missing.
  • Storage: one pre-allocated file per session, chunks written at their final byte offset as they arrive — so Assembly is a checksum pass, not a concatenation (issue #4).
  • Checksums are split by purpose (ADR 0002): CRC32C per chunk (fast, hardware-accelerated, catches accidental corruption early) vs. SHA-256 once over the whole file at Assembly (expensive but only paid once).
  • FAILED is terminal by design — a corrupted assembled file isn't trusted to resume from; the fix is a fresh Upload Session with a correct Manifest.
  • Abandoned sessions are reclaimed by a 24h-inactivity TTL sweep, not left to leak disk on a 25GB box.

Why this shape at all

Three properties fall out of "chunk + server-tracked bitset":

  • Bounded memory — the server never buffers a whole 5GB file; it writes each chunk to its offset and streams checksums.
  • Resumability — because the server tracks progress per chunk, a dropped connection loses at most one in-flight chunk, not the whole transfer.
  • Parallelism — chunks are independent, so a client can have 3-4 in flight at once without coordination beyond the index.
